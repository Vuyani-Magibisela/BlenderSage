Timeline
2026-10-16

Milestone 1, Step 2: guidance prototype

  • An 8-step desk-organiser lesson: size the box to 30 × 20 × 10 cm, apply the scale, bevel it, open the top, give the walls thickness, and add a Wood material.
  • The lesson shows up as an instruction card in the 3D Viewport (it can be collapsed and stays clear of the toolbar), an orange box around the target object, an outline on the editor to use, and the full step in the sidebar.
  • Steps complete themselves when the model matches, checked by mode, dimensions, scale, modifier settings and material. Mesh edits use manual confirmation. Back, Next and Skip never change the model or create undo steps.
  • If the target object can't be found, or several objects match, the learner selects it and clicks Use selected. Nothing is guessed, and no screen positions are stored.
  • Testing caught a lesson mistake: bevelling before applying the scale gives uneven bevels. The lesson now includes an “Apply the scale” step.
  • Tests: 35 unit tests and 20 in-Blender tests pass. The real install check passes. Card drawing averages under 1 ms (2.3 ms at worst) at interface scales 1.0 to 2.0.
  • Waiting on the 9-item hands-on checklist in docs/m1-findings.md.
2026-10-16

Milestone 1, Step 1: extension skeleton

  • Added blender_manifest.toml (id blendersage, version 0.1.0, Blender 5.2.0 or later, GPL-3.0-or-later). Blender's validator accepts it; the built zip holds only the extension's six files.
  • Added blender/lifecycle.py, the one place the extension adds handlers, timers, draw handlers and message-bus subscriptions. Disabling the extension removes everything recorded there.
  • Added a “Lesson” panel on a BlenderSage tab in the 3D Viewport sidebar. It shows “No lesson loaded” for now.
  • Tests: nine in-Blender tests pass on Windows and in the Linux container. Enabling and then disabling leaves no panel, handlers, timers or subscriptions. A separate check installs the built zip through Blender's extension system in a temporary user folder, then enables, disables and uninstalls it cleanly.
2026-10-16

Milestone 1, Step 0: API checks

  • Ran eight spikes against Blender 5.2.2 on Windows. Most open a fresh Blender window and drive it with simulated keyboard and mouse input.
  • Reports work as the action stream. Confirmed tools (grab, rotate, duplicate, extrude, typed values) and edits in interface fields and sliders produce reports with their final values. Each report has an ID that is unique within the Blender session. No cap was seen after 400 actions.
  • Gaps the state snapshots must fill: Dimensions edits leave no report; undo and redo leave no report but trigger handlers; reports are cleared when a file is opened; reports from other add-ons look the same as the user's.
  • Overlay drawing is cheap: about 0.3 ms per draw, 1.3 ms at worst, at interface scales 1.0, 1.5 and 2.0. The first draw costs about 80 ms. The card must avoid the toolbar, which overlaps the viewport by default.
  • Screenshots: the new Window.screenshot() returns the window's pixels in about 6 ms.
  • Results are in docs/m1-findings.md. At the checkpoint the design was approved: actions come from reports, with state snapshots covering the gaps. The journal and merge rules are now in docs/plan.md section 2, “Recorder design”, and the work is merged into main.

  • Container name is fixed as blendersage-dev so Claude Code on Windows can run tests with docker exec.

Dev container designed and planned

  • Chose a full VS Code Dev Container used by the developer; Claude Code stays on Windows, where it can also reach the Windows Blender 5.2 and the Blender MCP server for UI spikes.
  • The container deliberately does not cover viewport overlays, display scaling or Windows behaviour. Those stay on the Windows install with a manual checklist.
  • Wrote the design spec and a four-task implementation plan.
